# 教材デザイン指針

Module 2を実装して抽出した共通ルール。各Moduleの章数・順序・図の数は固定しない。

**2026年10月6日：初期のModule 2モデルを採用。** ユーザーの指定により、同じ共通デザインでModule 1と3〜7を追加した。章のまとまりや図は各トランスクリプトから決め、Module 2の章順やレイアウトを一律にコピーしない。

`prototypes/`のA・B・Cと`prototypes/focus/`は検討履歴として残す。通常の教材では`style.css`と`curriculum.css`を読み込み、試作専用のCSSや作品の例えを標準として引き継がない。

## 目的

AWS Skill Builderの動画を完全に置き換えず、トランスクリプトを「短時間で把握できる・後から復習できる・サービスの関係を復元できる」静的HTML教材に再編集する。読者が疑問を別途質問できる前提で、百科事典のように詳細化しない。認証、バックエンド、外部CDN、ビルド工程は不要。

## 解説文章

- 元データから学習テーマと重要な関係を抽出し、概念のまとまりで順序を組み直す。動画の順番や話者の世界観を引き継ぐ必要はない。
- 初出の用語は「何をするか」を短く説明する。サービス名だけを羅列しない。
- Webアプリ・バッチ・注文受付と配送など、役割が明確な技術例を優先する。
- 本文は概念、図は関係、キャプションは読み方と省略、補足は誤解を防ぐ条件、という役割分担にする。同じ説明を何度も繰り返さない。
- 台数、CPU目標、インスタンスタイプなどの例は、推奨設定や最新世代と誤認されないように「学習用の例」と書く。
- 元データの単純化が誤解を招く場合だけ補足する。付随する全サービスの解説へ広げない。
- 料金・仕様など変化する情報は最新のAWS公式資料を確認し、該当説明の近くにリンク、ページ末尾に資料一覧と確認日を置く。最大割引率を普遍的な条件として暗記させない。
- 原文と現在の仕様が異なるとき、黙って置換せず差異を記録する。今回確認した単純化への補足は、ユーザーの依頼範囲で実施した。

| --- | --- | --- | --- | --- |
| Compute | `--color-compute` / `--bg-compute` | `#a64d0b` | `#fff0dc` | EC2、ワーカー |
| Network・配置 | `--color-network` / `--bg-network` | `#23658a` | `#edf5fa` | Region、AZ、Subnet、ELB、APIの入口 |
| Monitoring | `--color-monitoring` / `--bg-monitoring` | `#7042a2` | `#f3edfa` | CloudWatch、観測の戻り線 |
| Control | `--color-control` / `--bg-control` | `#216b51` | `#eaf5ed` | Auto Scaling |
| Messaging | `--color-messaging` / `--bg-messaging` | `#a03268` | `#fbeef4` | SQS、SNS |
| Data・保存 | `--color-data` / `--bg-data` | `#12666c` | `#eaf5f5` | S3、EBS、EFS、DB、キャッシュ |

本文は`--ink: #202f3d`、補助文は`--muted: #576574`、ページ背景は`--paper: #faf9f6`、カードは白。色だけで区別せず、サービス名・役割・包含・方向を必ず併用する。未知のカテゴリに無条件で新色を追加しない。必要になった時点で役割の重複を検討する。

暗い面は学習目標カードだけに限定し、白い文字を使う。現段階ではライトテーマ。将来ダークテーマを追加する場合、カテゴリ名の意味を保って前景・背景をセットで変更し、コントラストを再確認する。

補足カードは青、重要ポイントは緑、誤解に注意するカードは橙。これは注記の種類であり、サービスカテゴリ色とは別の意味なので、タイトルに「補足」「重要」などを明記する。

## Typographyと余白

- 日本語対応のシステムフォント。外部Webフォントには依存しない。
- 本文16px、行間1.85。リード18px（モバイル16px）。章見出し24〜32px、ページタイトル30〜48px。
- 図のサービス名16px、役割14px。モバイルの単純フローでは13px以上。長いサービス名を収めるためだけに極端に縮めない。
- SVG内の主要文字16px、補助14px。viewBox幅820〜900、最小表示幅820pxを保持する。900幅の図でも表示文字は約14.6px以上を保ち、必要なら横スクロールで文字を守る。
- 12pxは資料リンク・ラベルなどの補助情報に限定する。本文や重要概念には使わない。
- カード内18〜28px、章間36〜52px。余白は概念のまとまりを示すために使う。
- CSSで`h1 → h2 → h3`の視覚階層とHTMLの見出し階層を揃える。コードだけ等幅フォント。
- 改行は画面幅に応じて調整する。日本語の禁則処理と`text-wrap: pretty`を補助として使い、見出しの意味の切れ目は編集して`.heading-part`、図のラベルは`.label-part`、短い重要用語は`.term`で保持する。均等な折り返しだけでは日本語の意味の切れ目は保証されない。長い句を改行禁止にしてはみ出させない。固定の`<br>`をページタイトルに埋めて画面幅を前提にしない。
- 320px幅ではページタイトルを26pxまで調整している。ホームのカード見出しは20〜26px。本文と図の文字は縮小しない。英語のサービス名・日本語の見出し・図キャプションを実際の表示で確認する。

## 図解の選択基準

図を作る前に「この図だけで何の関係を読み取れるべきか」を1文で決める。図解の種類の多さを目的にしない。ノードは原則「サービス名＋役割」の2段。

| 関係 | 表現 | Module 2の実例 |
| --- | --- | --- |
| 所属・包含 | 箱の中に箱 | 物理サーバーと仮想マシン、Region / AZ / Subnet / EC2 |
| 処理・通信 | 方向のある線 | フロントエンド → 内部ELB → バックエンド |
| 比較 | 左右で同じ比較軸 | Scale Up / Out、SQS / SNS |
| 収束 | 複数の入口から1つへ | Console / CLI / SDK → API |
| 分岐 | 1つの入口から複数へ | ALB → 別々のAZ、SNS → 購読先 |
| 継続的な制御 | 戻り線のあるループ | EC2 → CloudWatch → Auto Scaling → EC2 |

所属を矢印だけで表さない。通信を包含だけで表さない。矢印は「データ」「リクエスト」「観測」「制御」のどれかを明示し、往復を省くならキャプションで説明する。Module 2のSQS図はメッセージの移動方向を描き、受信要求はワーカーから行うと明記した。制御ループでは戻り線を破線にして役割を区別する。

図に省略したリソースがある場合、読み方を損なわない範囲で省略を明記する。AZ図ではVPCとALB用サブネットなどを省略し、完全な構築図ではないと説明している。包含は地理・配置の関係であり、VPCがAZを所有するという意味にしない。

## HTML/CSS・SVG・Mermaidの使い分け

| 方式 | 選択する条件 | このプロトタイプでの判断 |
| --- | --- | --- |
| HTML/CSS | 単純な包含、カード比較、直線的なフロー。文字折り返しと縦積みを活用したい | 仮想化、API収束、Scale Up / Out、内部ELB、SQS / SNS |
| SVG | 分岐・戻り線・入れ子が重なり、位置や線を正確に制御したい | CloudWatchのループ、ALBと複数AZの配置 |
| Mermaid | 大きすぎない関係図をテキストで管理する価値が高く、実描画の文字サイズと配置が適切 | 今回は不使用。ラベル折り返し・包含・戻り線を制御しやすいHTML/CSSとSVGを採用 |

Mermaidを新しいModuleで採用する場合はローカルの固定バージョンで提供し、オフライン表示・ライセンス・フォント・画面幅を検証する。すべての図を置換しない。未導入のライブラリに依存する図を先に置かない。

SVGの枠・ノード背景は共通CSSクラスを使う。`marker`のIDは同じページ内で一意にし、`title`・`desc`と`aria-labelledby`を付ける。座標とサービス構成は各ModuleのHTMLに残し、再利用するのはルールと見た目。色変更時はSVGの矢印ヘッドの色も同期する。

## 表を使う基準

同じ比較項目で複数の選択肢を並べる場合は表にする。Module 2ではインスタンスのカテゴリ、購入方法、操作方法、SQS/SNSを表で比較した。関係や動きが主題のときは図を選ぶ。

`caption`、`thead`、`th scope="col"` / `th scope="row"`を使う。表の文字を縮めて全幅に詰めず、最小幅720pxと`.table-scroll`を使う。比較軸が合わないものは注記する（例：専有ホストは割引方式とは別軸）。

「仮想化用」「メッセージング用」の部品は、その内容に合うときだけ使う。Module 2の全HTMLをコピーして文言だけ変えることを標準にしない。ページ固有の新パターンは実装してから、2つ目の用途が見えた時点で名前や共通化の必要性を見直す。

例：サービスカードと重要ポイントは、テーマに関係なく利用できる。

```html
<div class="service monitoring">
  <strong>Amazon CloudWatch</strong>
  <small>メトリクスを監視</small>
</div>
<aside class="note important">
  <strong>重要：監視と制御を分ける</strong>
  本文を短く書く。
</aside>
```

JavaScriptは目次の現在位置表示と印刷時の復習回答表示だけに使う。HTMLの本文・リンク・復習問題はJavaScriptを無効にしても利用できる。本文をJSで組み立てず、検索・認証・保存機能を追加しない。

## 可読性と検証

- 画面幅1280px、820px、390px、320pxでページ全体の横はみ出しを確認する。
- 狭い画面で比較パネルを縦積みにしても、サービスの関係と方向が変わらないこと。
- 複雑な図は最小幅を保持し、コンテナだけを横スクロールする。全体の関係が重要なら一枚の図を保つ。常に分割するルールにしない。
- スクロール領域に`tabindex="0"`、役割、ラベルを付ける。狭い画面ではスクロール案内を表示する。
- 色が見えなくてもサービス名・役割・配置から理解できること。主要な本文のコントラスト比4.5:1以上を確保する。
- キーボードでリンクと復習問題を操作でき、フォーカスが見えること。本文へのスキップリンクを保持する。
- 図の小さな補助文字、矢印の交差、ノード内のはみ出しを実際のブラウザーで確認する。
- 箱の幅とページの横はみ出しに加え、文字の描画範囲を確認する。単語の途中分割や「操作」の「作」だけが次の行になるような状態を見逃さない。部品が狭い場合は文字を小さくせず列数・配置を変える。
- 動きを減らす設定ではスムーズスクロールを停止する。印刷ではナビゲーションを隠す。
- 空リンク、重複ID、存在しないページへのリンクを作らない。

## 新しいModuleを追加する手順

1. この指針、README、該当するトランスクリプトを読む。番号と入力内容を確認し、指示と現状に差異がある場合は確認する。
2. 学習目標を3〜5項目に整理し、概念のまとまりと関係を先に決める。
3. 仕様の単純化・料金・用語を最新のAWS公式資料で確認。新しいModuleの内容やタイトルは元データから決め、推測しない。
4. `modules/module-NN.html`を作る。共通ヘッダー・目次・学習目標・本文・必要な図表・重要ポイント・復習・資料・Home導線を設ける。章数や図の方式は内容から決める。
5. `style.css`・`curriculum.css`と共通JSを相対パスで読み込む。カードや注記は既存クラスを利用する。SVG座標や図の内容はページ内に置く。
6. 視覚検証後、再利用価値のある新しいパターンだけをCSSとこの指針へ追加する。Module番号を含むCSSセレクターを増やさない。
7. `index.html`の学習モジュール欄へカードを追加。公開済みモジュールが隣接したら、両ページのPrevious / Nextを実在するリンクへ変更する。未公開は非リンクの表示を維持する。
8. 公開数とREADMEを更新する。ページ幅、文字サイズ、図の方向、ローカルリンク、目次、復習問題、オフライン表示を確認する。

## Module 2で得た設計判断と次の評価

実装上の判断として、入口の収束はCSS、制御の戻り線とAZの配置はSVG、リソースの選択肢は表に分けると、それぞれの関係を表しやすかった。モバイルでは比較パネルを縦積みにし、複雑な図は横スクロールにした。これは表示・構造の検証結果であり、学習効果が実証されたという意味ではない。

次の評価では、初学者に「CloudWatch・Auto Scaling・ELBの違い」「SQSとSNSの違い」を図だけで説明してもらう。回答の正確さ、必要な箇所に戻る速さ、横スクロールの気付きやすさを確認する。料金セクションの情報量、長いページでの読み疲れ、SVGのモバイル操作は改善候補。実ユーザーでの学習評価と複数ブラウザーの検証はまだ未実施。

## Module 1〜7で追加した表示ルール

- 長い見出しは意味の切れ目で短い`.heading-part`に分ける。章番号を除いた見出し領域にも収まることを確認する。
- 本文の短い専門用語や述語を`.term`で保持する場合、直後の句点・読点・閉じ括弧も同じ要素へ入れる。`<span class="term">確認します。</span>`のようにし、句点だけが行頭へ送られる状態を防ぐ。開き括弧も必要に応じて用語と一緒に保持する。
- すべての語句を改行禁止にしない。長い用語は短い意味単位に区切り、文章の編集とレイアウト変更を優先する。`text-wrap: pretty`だけに任せない。
- 学習目標の番号と文章は`<p><b>01</b><span>説明文</span></p>`にする。flexの直接の子に用語spanを並べると、本文が別々の列になってしまう。
- 複数の入れ子はモバイルで枠の余白を12pxに調整し、文字の領域を確保する。所属関係をなくすために枠を消さない。
- 単純フローやカードの列数は、狭くなる前に縦配置へ変える。大きな図と表だけは専用の横スクロール領域にする。ページ全体を横に流さない。
- SVGのノード色・矢印色・線・文字を明示する。未定義クラスのまま黒く塗られたノードを作らない。経路の番号や説明を線上へ重ねない。
- 目次移動は即時スクロールにする。図を追うためのアニメーションは追加しない。
- 320 / 390 / 600 / 820 / 1093 / 1280px幅で、ページと文字の描画範囲、語の途中分割、短すぎる末尾行、行頭の句読点、図の配置を確認する。復習の回答と補足カードも確認対象に含める。
- DOMの寸法確認に加え、実際の画面で図・文字・矢印を目視する。測定の成功だけで表示確認を済ませない。

今回の入力との対応・補足・表示検証は`curriculum-review.md`を参照。表示確認と、読者の理解度の検証は別に扱う。
