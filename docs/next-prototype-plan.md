# 次の比較方針（サンプル実装済み・選定中）

2026年10月6日のフィードバックを受けた記録。

- Cは不採用。作品の例えから展開する形式は、無理な対応と追加の情報量につながる。
- A・Bは既存案との見た目・読み方の差が不足し、選択の材料にならなかった。色や章順の変更を別の学習体験とみなさない。
- 共通UIの改行と配置は、候補を選ぶ前に修正する。ページ全体の横はみ出しがないことだけで可読性を判定しない。

## 次に比較する3方向

| 方向 | 実際のページ構造 | 既存との差 | 判断すること |
| --- | --- | --- | --- |
| 図に注釈する | 大きな構成図の周囲に、役割・矢印・重要な条件の説明を置く。本文は短い要点と必要な補足に限定 | 文章カードを順に読む構造から、図の中の関係を追う構造へ変える | 図を見てサービスの役割を説明できるか |
| 構成の変化を見せる | 基本構成 → 問題が起きた構成 → 改善した構成を並べ、追加した要素と理由を直接注記する | 冒頭に状況カードを足す形式から、構成自体の変化を主役にする形式へ変える | 何が必要になったか、改善前後の違いが分かるか |
| 問いから確認する | 短い問いと図を示し、自分で考えてから説明を開く。最後に判断の軸を整理する | 最初から説明を連続して読む形式から、判断して答え合わせする形式へ変える | 勘違いを発見できるか、操作が負担にならないか |

推奨は「図に注釈する」を基本にし、スケーリング・分散・疎結合などの変化が重要な箇所で「構成の変化」を使うこと。「問いから確認する」は復習に使う。ただし、この組み合わせを採用済みとして扱わない。

## 進め方

CloudWatch / Auto Scaling / ELBの同じ1テーマで3方向の見せ方を比較する。色と文字サイズ、扱う概念の範囲を揃え、レイアウト・説明の置き方・読む動作を明確に変える。方向が決まったらModule 2全体へ展開する。

この比較方針はユーザーの承認を受け、`prototypes/focus/`に3つのサンプルと比較の入口を実装した。今回扱うのはCloudWatch・Auto Scaling・ELBの役割と連携。見せ方を選んでからModule 2全体へ展開する。既存・A・Bは検討履歴として維持し、Cは不採用の履歴として折りたたんでいる。Module 3以降へは進まない。

## 改行とUIの確認方法

2026年10月6日に共通CSSとHTMLラベルを修正した。API図は狭い画面で3つの入口を縦配置にし、右側の接続線からAPIへ収束させる。仮想化・短いフロー・説明の対比も、狭い領域に複数列を押し込まない。本文・役割の文字サイズは保持する。

見出しは意味のまとまりを編集して`.heading-part`、図の短いラベルは`.label-part`、重要な短い用語は`.term`を使う。すべての文章を改行禁止にしない。長い文は通常の日本語の禁則処理で折り返す。均等な行長を作るCSSだけで意味の切れ目が保証されると考えない。

各部品について、箱の寸法に加えて文字の描画範囲、英単語の途中分割、長い用語、末尾だけの行、矢印・ノードの関係を確認する。320 / 390 / 600 / 820 / 1093 / 1280px幅で表示を調べる。CSS更新時にはキャッシュを更新した表示で確認する。

旧試作の改行修正時の表示検査では4ページ×6幅の24条件でページ全体・見出しの箱・英単語の描画範囲の横はみ出しと途中分割がないことを確認した。元の検証に含めていなかった文字の範囲も調べた。比較表は720px以上の幅を保持し、カテゴリ名を意味のまとまりで折り返す。確認画像は`module-02-wrap-fix-mobile.jpg`と`module-02-wrap-fix-320.jpg`。これは読みやすさを保証する学習評価とは区別する。
